# 简历 JD 匹配优化 · 踩坑点清单

本文件记录从「JD + 原始简历」生成聚焦版简历过程中真实踩过的坑。每次执行前扫一遍，避免重蹈覆辙。按「主题」分类，每条含现象、原因、正确处理。

---

## 1. 规模自贬（最常见）

- **现象**：原简历写「独立负责中小型客户项目」，但实际客户是某上市集团 A、B 等**上市集团**。
- **坑**：自贬规模等于主动放弃 JD 的「大客户项目管理 / 复杂决策链突破」得分。
- **正确**：确认可升级后，改为「服务某上市集团 A、B 等上市及中大型企业客户」，并点出「长决策链、多部门协同、复杂环境」。只写真实情况，不虚构。
  - **数字必须有出处**：「20+」这类数量词只能来自原简历或用户明确提供的事实，不得为显得有分量顺手补上。交付前走 SKILL.md Step 5 事实回查。

## 2. 高层叙事夸大

- **现象**：JD 写「和 CTO / 业务 Leader 建立技术互信、影响数字化转型方向」。
- **坑**：若用户实际只对接 IT 负责人，硬写「和 CTO 建立互信」= 造假，面试一问就崩。
- **正确**：主要对接 IT 负责人 → 用「IT 负责人与业务方」「技术互信 / 方案影响力」措辞；只有用户确认真有高层对接案例，才写高层叙事并要其提供具体场景。

## 3. 无证据方向硬编

- **现象**：JD 列了「智能营销 / 智能客服 / 数据治理 / 供应链」多个方向，简历只在其中 1-2 个有证据。
- **坑**：为了「全覆盖」去编造没做过的方向，面试必露怯。
- **正确**：选证据最强的方向打「专家」主线；其余方向用代表项目摆真实证据覆盖；零证据的方向（如营销）宁可留白或补「学习叙事」，不硬凑。

## 4. 英语短板规避

- **现象**：外企或含海外客户的岗常需英语，但候选人英语能力可能有限且多年未用。
- **坑**：主动写「英语流利」= 造假；完全不提又可能漏掉硬要求。
- **正确**：国内岗直接不碰英语模块；若为外企/海外岗，仅在用户确认后补「可英文自我介绍兜底」，不夸大水平。

## 5. 竞品 / 母公司敏感词避雷（高危）

- **现象**：简历项目涉及跨境 ERP、二次开发等，可能用到「逆向内部接口」「JWT 复用 / Cookie 重放」「比浏览器点击更快」等表述。
- **坑**：若目标公司是某互联网大厂体系内的巨头，这类灰产/逆向手法表述极度敏感，写上去像在炫耀漏洞利用，直接减分甚至风险。
- **正确**：一律改口为「基于 ERP 接口能力做系统集成与自动化编排」「内部 Web 接口集成」等中性、合规表述。

## 6. 业务成果雷（量化边界）

- **现象**：AI / 自动化项目想用「出单 / GMV / 业务增长」证明价值。
- **坑**：很多项目（如铺货 Skill）README 自己都承认「铺完 ≠ 出单，出单取决于运营」。拿业务结果吹 = 无依据。
- **正确**：只拿**工程指标**作证：拦截率、发布成功率、效率提升 %、人工投入下降 %。业务结果除非用户能提供确凿数据，否则不写。

## 7. 链接处理（排版）

- **现象**：案例 / 仓库 / 文档给的是裸 URL，占大半行、丑、干扰阅读。
- **坑**：裸链接在 Markdown 预览和转 PDF 时都难看，且容易在转换中丢失。
- **正确**：全部转 Markdown 内嵌可点：`[客户案例](URL)`、`[GitHub 仓库](URL)`、`[name@example.com](mailto:...)`。显示文字写中文短词，URL 藏起来。

## 8. 案例无量化数字的定位

- **现象**：客户官方公众号/官网报道作为佐证，但文章本身没有「效率提升 X%」「覆盖 N 门店」等数字。
- **坑**：当成「量化成果」吹会露怯；完全不引又浪费公开背书。
- **正确**：定位为「案例证明 / 公开背书」（credibility 拉满、可验证），措辞用「主导 XX 业务落地（案例见客户官方公众号）」，不附量化数字；若用户能回忆出数字，再补进 bullet。

## 9. 结构：子项嵌套 vs 独立成条

- **现象**：在工作经历段插入一条「XX 客户深度交付」作为独立 bullet，打断了并列的能力主题结构。
- **坑**：读起来像塞了个客户 logo，逻辑混乱；能力主张与证据分离。
- **正确**：把具体客户实例作为「能力主题 bullet」的**下钻子项**（缩进嵌套），形成「主张 + 证据」结构。代价是曝光度略低，但结构更干净，且强钩子（独立接口负责人 / 多年信任）仍保留在子项里。

## 10. 并行编辑冲突（工具层坑）

- **现象**：在同一轮里对同一个文件发多个并行 Edit，部分改动没落盘（如邮箱 mailto 那次）。
- **坑**：并行编辑会互相覆盖或静默失败，导致文件状态与预期不符。
- **正确**：对同一个文件的多次编辑**串行执行**；每次批量改动前先 `Read` 最新内容确认真实状态，再 Edit；改完 `Read` 一次校验。

## 11. 文件命名规则

- **现象**：文件名随意（如「简历优化_某厂FDE.md」）。
- **坑**：多岗位多版本时找不到、易混。
- **正确**：统一 `名字_岗位名称.md`（如 `候选人_AI业务分析师.md`）。注意岗位名可能中途变化，以用户最终确认的岗位为准重命名。

## 12. PDF 导出路线（环境层坑）

- **现象**：用户要求「导出 PDF」。
- **坑 A**：想用 SQL 生成 PDF —— **不可能**。SQL 只取数，PDF 渲染必须靠报表工具（SSRS/Jasper/Crystal）或代码库（ReportLab/FPDF/iText）。本任务是本地 md→PDF，SQL 彻底不对路。
- **坑 B**：**只看 PATH 里的命令行工具会误判「没有渲染引擎」**。macOS 上 Chrome 装在 `/Applications`，`which chromium` 找不到但实际存在。实测：`pandoc / weasyprint / wkhtmltopdf / xelatex / chromium / libreoffice` 全空，但 `/Applications/Google Chrome.app` 存在 → 直接能出高质量 PDF，**不必装 fpdf2/weasyprint**。
- **正确（按优先级）**：
  1. **探测**：`which pandoc weasyprint wkhtmltopdf xelatex chromium libreoffice soffice`；再查 `.app`：`ls -d "/Applications/Google Chrome.app" "/Applications/Microsoft Edge.app"`；查字体 `ls /System/Library/Fonts | grep -iE "pingfang|songti|heiti"`。
  2. **有 Chrome/Edge → 首选（本机实测最漂亮、零安装）**：自写 Python 脚本 md→HTML（`**粗**`→`<strong>`、`[文字](url)`→`<a>`、`- `→`<ul><li>`），配 CSS（`PingFang SC` + `@page{size:A4}`），再：
     ```
     "/Applications/Google Chrome.app/Contents/MacOS/Google Chrome" \
       --headless=new --disable-gpu --no-sandbox \
       --user-data-dir=/tmp/cr-<每次换新> --no-pdf-header-footer \
       --print-to-pdf="out.pdf" "file:///tmp/resume.html"
     ```
     加粗、链接、中文、分页全部原生支持。
  3. 有 pandoc + LaTeX/weasyprint 后端 → `pandoc in.md -o out.pdf --pdf-engine=...`。
  4. 都没有 → 兜底：`pip3 install fpdf2`（快，自写解析）/ `brew install` pango+cairo 后 `pip3 install weasyprint`（美）。
- **四个必踩坑**：
  - **a. 显式白底**：CSS 必须写 `html, body { background:#ffffff; }`，否则用 `sips` 转 PNG 预览时透明背景会被合成成黑色（误以为 PDF 是黑底）。
  - **b. Chrome 缓存**：微调版式后必须换**全新** `--user-data-dir`，复用旧目录可能读到缓存，导致「改了没效果」的误判。
  - **c. 页数统计别用正则**：`/Type /Page` 正则会数错；用 `pip3 install pypdf` + `PdfReader(path).pages` 准确计数。想判断第 2 页溢出了多少，用 pypdf 提取第 2 页文本长度（<200 字 = 明显没排满，应压成一页）。
  - **d. 邮箱可能是尖括号自动链接**：md 里的邮箱常被编辑器自动转成 `<a@b.c>` 格式（合法 Markdown autolink）。自写解析器若只认 `[文字](url)`，会把尖括号转义成字面文本且**丢失 mailto 链接**。转义后补一条：`&lt;(邮箱)&gt;` → `<a href="mailto:…">…</a>`。交付前用 pypdf 检查页 1 是否有 `mailto:` 注释。
- **一页收口经验**：先按 10.4pt 排；若溢出 ≤6 行，压到 **9.5pt / 行高 1.38 / 边距 9–12mm** 通常能进一页；仍溢出说明内容真超一页，**不要再压字号**（低于 9pt 印刷吃力），改为分两页或替换项目。

## 13. 代表项目数量与替换

- **现象**：想多塞项目显丰富，或新增项目时保留旧的导致堆砌。
- **坑**：项目越多越稀释主线， recruiter 抓不住重点。
- **正确**：代表项目保持 **4 个左右**；要用更强/更贴 JD 的项目时**替换而非叠加**（如用「可控 AI Agent 业务自动化」替换「飞书账单录入」），使总数恒定、结构不乱。

## 14. 邮箱笔误

- **现象**：原简历邮箱写成 `mailto:name@example.com`（把协议当前缀）。
- **坑**：裸 `mailto:` 不是合法显示，且不可点。
- **正确**：写成可点格式 `[name@example.com](mailto:name@example.com)`。

## 15. 「对应 JD」标注要删（交付净化）

- **现象**：为便于映射，在代表项目标题后加「（对应 JD：AI 产品应用 / 方案演示）」这类标签。
- **坑**：这是内部对齐用的记号，交付给用户/HR 的简历里就是噪音。用户几乎一定会要求删除（实测：生成后第一句反馈即「把简历中这些备注信息删除」）。
- **正确**：草稿阶段可在内部映射，**交付版一律删除**。JD 关键词已织进 bullet 正文，标题只保留「项目名｜能力定位」，不挂任何「对应 JD」标签。

## 16. 个人优势首版就要极简

- **现象**：首版个人优势每条写成 60–80 字长句，用户随后要求「更加简洁」返工。
- **坑**：优势段复述下文细节、堆量化数字，读起来累，扫读性差。量化数字与项目细节本就该下沉到代表项目段。
- **正确**：每条严格「**加粗标题 + 一句**」，一句控制在约 40–50 字；**量化成果全部下沉到代表项目**，优势段只留能力定性；标题别与项目名重复。

## 17. 售前岗要砍掉售后动作（培训 / 答疑 / 交付 SOP）

- **现象**：简历里写「组织线上/线下客户培训」「日常答疑」「沉淀交付 SOP」等。
- **坑**：这些是**成交后 / 交付期**的事，属于实施、客户成功、技术支持。售前岗的 JD 支柱是需求沟通、Demo 搭建、演示迭代、方案设计、内部交接，**没有培训与交付**。写多了会把候选人归类成「技术支持/实施」，稀释「售前」定位——尤其当过「技术服务工程师」的人，履历本就偏交付，更要主动做减法。
- **正确**：售前岗一律弱化或删除培训、答疑、交付 SOP；笔墨集中在「方案演示 + 业务价值讲解 + 反馈迭代 + 方案/演示材料沉淀」这些**售前动作**上。「交付 SOP」改「演示材料」，对齐 JD 的「编写解决方案、演示材料、需求说明」。判断口诀：**成交前说的是售前，成交后干的是售后**。

## 18. 简历去重：同一招牌只打一次

- **现象**：同一工具名/关键词（如 Codex、Vibe Coding、RAG/Agent/MCP）在个人优势与多个项目里反复出现；个人优势复述工作经历的客户名与数字；同一段多条 bullet 都讲「演示」。
- **坑**：重复不增加说服力，反而稀释重点、显得堆砌，recruiter 抓不住每条 bullet 的独立价值。
- **正确**：
  - **招牌关键词只打一次**：把 Codex / Vibe Coding 集中到最强的那个项目，其余项目删掉同类表述。
  - **优势段不复述经历细节**：客户名、数字下沉到工作经历，优势只留能力定性（呼应 #16）。
  - **相邻优势不重复枚举**：同一组技术栈（RAG/Agent/MCP）只在一处列出，其余用「AI 能力」概括。
  - **同段 bullet 按 JD 支柱分工**：一条管需求沟通、一条管演示迭代，别两条都写「演示」。

## 19. 用本 JD 原词，别套旧 JD 词汇

- **现象**：沿用上一份简历/上一个 JD 的关键词（如「横向拉通」来自上一份 JD），而本 JD 原话是「协调内部资源」。
- **坑**：HR/ATS 按本 JD 用词筛，套错词等于没命中，还显得模板化。
- **正确**：改写前先把本 JD 的高频动词/名词抄下来（如「协调内部资源」「演示与快速迭代」「方案设计与项目支持」），逐条回填**本 JD 原词**，不要跨 JD 复用。每换一个 JD 就重抄一遍词库。

## 速查：一句话决策

| 遇到 | 做 |
|---|---|
| 客户是上市公司却写「中小客户」 | 升级为「大客户复杂度」，只写实、不新增数字 |
| 终稿出现原简历没有的数字 / 规模 | 跑 SKILL.md Step 5 事实回查，未确认即删 |
| JD 要高层对话但只对接 IT | 弱化为「技术互信/方案影响力」 |
| JD 列的方向零证据 | 不硬编，留白或补学习叙事 |
| 项目涉及逆向/灰产手法 | 改中性合规表述 |
| 想用出单/GMV 证明 | 改用工程指标 |
| 裸 URL | 全转 `[文字](URL)` |
| 客户报道无数字 | 当「案例证明」不量化 |
| 客户实例插断并列结构 | 嵌套成子项 |
| 同文件多次改 | 串行 + 改前 Read |
| 导出 PDF | 不碰 SQL；优先 Chrome 无头 print-to-pdf |
| 项目太多 | 替换不叠加，约 4 个 |
| 项目标题挂了「对应 JD」 | 交付版一律删 |
| 个人优势写成长句 | 每条约 40–50 字，数字下沉项目 |
| 售前岗写了培训/答疑/交付 SOP | 删售后动作，只留演示/方案/迭代 |
| 同一关键词多处出现 | 只留最强的那个项目，其余删 |
| 套用了上一个 JD 的词汇 | 换成本 JD 原词，重抄词库 |
